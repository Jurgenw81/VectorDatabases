Understand vector databases in depth

What is a vector database?

A database optimized for storing, indexing, and querying vector embeddings — numerical representations of data like text, images, or audio. Instead of exact matches, it finds the most similar items.

Vectors, not rows

Instead of columns and rows, it stores dense vectors (e.g., 768 dimensions). Each vector captures semantic meaning. A sentence, an image, or a song becomes a list of floating‑point numbers.

For example, the vector for "king" minus "man" plus "woman" is approximately equal to the vector for "queen" — this is the famous word2vec analogy.

Similarity search

Queries return the most similar vectors using distance metrics like cosine similarity, dot product, or Euclidean distance. You search by meaning, not by exact keywords.

This is why you can search for "furry animals" and find images of cats, even if the word cat never appears in the metadata.

Built for AI

Essential for LLM memory, recommendation engines, image retrieval, and anomaly detection. They handle the high‑dimensional data that traditional databases struggle with.

In a RAG pipeline, a vector database retrieves relevant context for an LLM, dramatically improving the accuracy of generated answers.

"Vector databases are to AI what relational databases were to the web — the foundational infrastructure that unlocks a new generation of applications."

— Industry consensus

Embeddings

An embedding is a learned representation where similar items are close together. A model like BERT or CLIP converts raw data into these vectors. The database then indexes them for fast retrieval.

Common embedding dimensions: 384 (MiniLM), 768 (BERT‑base), 1536 (OpenAI ada‑002), 3072 (OpenAI text‑embedding‑3‑large).

Indexing (ANN)

Exact nearest neighbor search is too slow for millions of vectors. Approximate Nearest Neighbor (ANN) indexes like HNSW, IVF, or ScaNN trade a tiny bit of accuracy for massive speed gains.

HNSW can search billions of vectors in milliseconds with 95–99% recall — the exact trade-off is tunable.

Metadata filtering

Most vector DBs let you combine vector similarity with metadata filters (e.g., "find similar images where date > 2024"). This hybrid search is crucial for real‑world applications.

Without metadata filtering, you'd have to retrieve hundreds of results and filter them in your application — slow and memory‑heavy.

How does it work?

From raw data to fast nearest‑neighbor search — typically in four steps. This pipeline is the backbone of modern AI applications.

1

Generate embeddings

Use a machine learning model (like BERT, CLIP, or OpenAI) to convert text, images, or audio into a vector of numbers. For example, the sentence "The cat sat on the mat" might become a 768‑dimensional vector. This vector captures the semantic meaning of the input.

The quality of your embeddings directly determines the quality of your search. Garbage in, garbage out.

2

Store & index

The vector database stores vectors and builds a specialized index (e.g., HNSW, IVF) to enable fast approximate nearest neighbor search. The index organizes vectors so that similar ones are grouped together, allowing the database to skip most of the data during a query.

You also store metadata alongside each vector — things like the original text, a URL, a timestamp, or a user ID.

3

Query with a vector

You provide a query vector (e.g., "pictures of cute animals"). The database compares it against indexed vectors using a distance metric. Because the index is approximate, it can return results in milliseconds even with billions of vectors.

You can combine this with metadata filters — for example, only search images uploaded in the last week.

4

Get similar results

It returns the top‑k most similar vectors and their associated metadata — fast, even with billions of vectors. You can then use these results to power search, recommendations, or LLM context. This is the core of retrieval‑augmented generation (RAG).

Typical response includes the vector ID, similarity score, and any stored metadata.

# Example: querying a vector database (pseudo‑code)
from vectordb import Client

client = Client("your-api-key")
collection = client.get_collection("images")

# 1. Generate embedding for the query
query_vector = model.encode("a cute kitten")

# 2. Search for similar vectors
results = collection.query(
    vector=query_vector,
    top_k=5,
    filter={"category": "animals"}
)

# 3. Use the results
for r in results:
    print(r.id, r.score, r.metadata)

Vector DB vs. traditional database

Key differences in data model, querying, and typical use cases. Vector databases complement — not replace — traditional systems.

Aspect Traditional (SQL / NoSQL) Vector database
Data model Rows, documents, key‑value High‑dimensional vectors + metadata
Primary query Exact match, range, joins Similarity (nearest neighbor)
Index type B‑tree, hash, inverted HNSW, IVF, Annoy, PQ
Typical use Transactions, records, analytics Semantic search, RAG, recsys
Scaling focus ACID, concurrency Low‑latency ANN, high‑dim
Query example SELECT * FROM users WHERE age > 30 FIND SIMILAR TO [0.2, 0.8, ...]

Many modern databases (PostgreSQL, Redis, Elasticsearch) now offer vector extensions, blending both worlds.

Distance metrics explained

How does a vector database decide what is “similar”? It calculates the distance between vectors. Here are the most common metrics.

Cosine similarity

Measures the angle between two vectors, ignoring magnitude. Ideal for text embeddings where direction matters more than length. Score ranges from -1 to 1 (1 = identical direction).

Euclidean (L2)

The straight‑line distance between two points. Use when magnitude is important, like in image or audio embeddings. Smaller values mean more similar.

Dot product

A measure of alignment that combines both angle and magnitude. Often used in recommendation systems. Larger positive values indicate higher similarity.

"Choosing the right distance metric is critical. Cosine similarity is the go‑to for text, while Euclidean is often better for image data. Always validate with your own data."

— Best practice from ML engineers

Indexing algorithms (ANN)

Exact search is O(n) — too slow for millions of vectors. Approximate Nearest Neighbor (ANN) indexes make it fast.

HNSW

Hierarchical Navigable Small World. A graph‑based index that is fast and accurate. It's the most popular choice for in‑memory vector search.

IVF

Inverted File Index. Partitions vectors into clusters. At query time, only the nearest clusters are searched. Great for very large datasets.

PQ / Quantization

Compresses vectors to reduce memory and speed up search. Often combined with IVF or HNSW. Trades a bit of recall for huge efficiency gains.
