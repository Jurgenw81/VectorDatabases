The point of the project

What is a vector database?

A normal database is great at exact values: IDs, names, dates, categories. A vector database is designed to store high-dimensional vectors and retrieve the vectors that are mathematically closest to a query. That makes similarity and semantic search possible.

01 · EMBEDDING MODEL

CLIP creates meaning as numbers.

CLIP converts an image or text query into an embedding: a vector whose position represents learned semantic information.

  • Input: image or text
  • Output: vector
  • Job: representation
→
02 · VECTOR DATABASE

Qdrant stores and searches those numbers.

Qdrant stores each vector as a point together with an ID and payload metadata, then retrieves nearest points using a similarity metric.

  • Input: vectors + metadata
  • Output: nearest matching points
  • Job: storage + retrieval
One sentence for the whole video: CLIP turns meaning into vectors. Qdrant is the vector database that stores those vectors and finds the closest ones.

Step 2 · the actual vector database

Qdrant stores more than “just an array.”

In Qdrant, a stored item is a point. A point can contain an ID, a vector, and a payload. The payload is ordinary metadata that lets your application map the numerical vector back to the real file and filter results later.

Plain vector index

A similarity-search index focuses primarily on nearest-neighbor lookup. You often maintain metadata and persistence separately.

Vector database

Qdrant manages collections of points containing vectors and payload, persists them, supports updates/deletes, filtering and vector queries through a database API.

Step 3 · collections

A collection defines how your vectors are stored and compared.

For the image collection, we create a Qdrant collection whose vector size matches the CLIP embedding dimension and choose cosine distance for similarity.

create_collection.pyQdrant schema
from qdrant_client import QdrantClient, models

client = QdrantClient(path="./qdrant_data")

client.create_collection(
    collection_name="images",
    vectors_config=models.VectorParams(
        size=embedding_dimension,
        distance=models.Distance.COSINE,
    ),
)

For a tutorial, Qdrant's Python client can run with local on-disk storage. You can later switch to a Qdrant server without changing the core vector-search concept.

Step 4 · inserting points

Indexing means: embed the file, then upsert the vector into Qdrant.

index imageCLIP → Qdrant
# Turn image pixels into a vector
embedding = clip_model.encode(image).tolist()

# Store the vector AND useful metadata in the vector database
client.upsert(
    collection_name="images",
    points=[
        models.PointStruct(
            id=point_id,
            vector=embedding,
            payload={
                "path": str(image_path),
                "filename": image_path.name,
                "type": "image",
            },
        )
    ],
)
This is the database moment: the embedding is no longer just a Python list. It becomes a persistent database point associated with metadata about the file it represents.

Similarity determines the ranking

With cosine distance configured for the collection, Qdrant ranks points according to vector similarity. Conceptually, vectors pointing in similar directions receive stronger similarity.

Why use a vector database?

Because semantic search needs more than SQL equality.

VEC

Vector storage

Store high-dimensional embeddings as first-class database data.

NN

Similarity search

Retrieve nearest vectors instead of only exact-value matches.

PAY

Payload metadata

Keep filenames, paths, types and other application data with each point.

FLT

Filtering

Combine vector similarity with metadata constraints as the project grows.

CRUD

Database operations

Add, update and delete points instead of rebuilding a standalone array by hand.

API

Real database interface

Run locally for the tutorial, then connect to a Qdrant service using the same model.

Important retrieval concept

“Closest” does not automatically mean “correct.”

If you search for something that is not represented in your collection, the database can still return the nearest vectors. A nearest-neighbor query answers “what is closest among what I have?”, not “does an objectively correct match exist?”

Top-K retrieval

“Give me the 5 nearest points.” Even weak matches may appear because the database is required to rank something.

limit=5

Score threshold

For some applications you can reject results below a calibrated similarity threshold so poor matches are not presented as valid.

Python architecture

The responsibilities stay clean.

mental_model.pyCLIP ≠ Qdrant
# CLIP's job: representation
image_vector = clip.encode(image)
query_vector = clip.encode("dog playing in snow")

# Qdrant's job: database storage + similarity retrieval
client.upsert(collection_name="images", points=[...])
matches = client.query_points(
    collection_name="images",
    query=query_vector.tolist(),
    limit=5,
).points
Do not say “Qdrant understands the image.” CLIP creates the semantic representation. Qdrant does not know what a dog is; it stores vectors and finds mathematically similar vectors.
